# Copper Pipes — Fabric mod for Minecraft 26.3

## Goal
Lightweight item sorting system: copper pipes with glass walls connect chests; items visibly flow
through pipes and are sorted into chests by filter cards. Must be far cheaper on the server than
copper golems: no entities, no per-tick scanning, event-driven, cached network.

## Tech
- Minecraft 26.3, Fabric Loader + Fabric API, Java 25, Gradle wrapper, Fabric Loom (latest for 26.3).
- 26.x is unobfuscated: use Mojang official names only (no Yarn).
- Look up current versions at https://fabricmc.net/develop before setting gradle.properties.
- Start from the official Fabric example mod (github.com/FabricMC/fabric-example-mod), split sources (main/client).
- Mod id: `copperpipes`, package: `pl.misiek.copperpipes`.
- Host OS: Windows — use `gradlew.bat` / `.\gradlew`.

## Content
Blocks
- `copper_pipe` (+ exposed, weathered, oxidized, and waxed variants): copper frame + glass walls,
  auto-connects to pipes and connectors in 6 directions (multipart blockstate). No block entity, no ticking.
  Oxidation stage = speed multiplier (1.0 / 0.7 / 0.45 / 0.25). Axe scrapes, honeycomb waxes (vanilla behaviour).
- `inlet_connector`: attached to a container face, pulls items from it into the network.
- `outlet_connector`: inserts into the attached container. Has 1 slot for a Sorting Card (does not use chest slots).
  Outlet without a card = overflow.
Items
- `sorting_card`: data component with list of rules + priority (0–9) + mode (whitelist/blacklist).
  Rule syntax: `#namespace:tag`, `namespace:item`, `@modid`, `!rule` (exclude).
  Right-click opens edit GUI: rule list, text field with tag autocomplete, ghost slot that suggests the held item's tags.
  Crafting: card + paper = copy.
- `pipe_wrench`: rotate connectors, toggle a pipe arm, shift = pick up.

## Performance rules (hard requirements)
- Network graph is rebuilt via BFS only when a pipe/connector is placed/removed (mark dirty, rebuild lazily).
- Compile card rules into a cache `Item -> outlets sorted by priority`; expand tags at build time only.
- Paths (inlet -> outlet) computed once per rebuild and cached.
- Inlets tick ONLY when active; wake on container change; sleep when empty. Move up to N items every X ticks (X depends on oxidation).
- Items in transit: server-side queue sorted by arrival tick; check only the head each tick (O(1)).
  On pipe break, drop in-transit items.
- Use Fabric Transfer API (`ItemStorage.SIDED`) for all container access, so modded chests work.
- Visuals client-only: server sends one packet per transferred stack (item, path, start tick, speed);
  client renders items moving along the path. Config: enable/disable, render distance (32), max visible items (200).

## Milestones (do in order; each must build and be testable in-game)
1. Project setup, mod loads (`.\gradlew build` passes, runClient starts).
2. `copper_pipe` block with item, texture, creative tab, recipe.
3. Auto-connection (multipart blockstate, 6 directions).
4. Frame + glass model, translucent render layer, oxidation + waxing variants.
5. Inlet/outlet connectors with block entities, moving items without filters.
6. Network manager: BFS, path cache, transit queue, dropping items on break.
7. Sorting card: data component, rule parser + matcher, outlet slot, priority, overflow.
8. Card edit GUI + networking, copy recipe.
9. Client renderer for flowing items + config.
10. Pipe wrench, polish, lang files (en_us + pl_pl).

## Working rules
- After each milestone: run `.\gradlew build`, fix all errors, commit to git with a clear message,
  then stop and tell the user what to test in-game (exact steps).
- Write Fabric gametests for network logic (sorting, priority, overflow, break drops) where possible.
- Keep code simple and readable; no premature abstractions. Comment only non-obvious logic.
- If an API name is uncertain, check Fabric docs / decompiled sources in the Loom cache instead of guessing.
- Placeholder textures are fine (simple 16x16 PNGs generated by script); note them for later replacement.
